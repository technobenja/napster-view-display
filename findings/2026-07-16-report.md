## Root cause: broken local screencapture, not a display fact

Three local captures, over an hour apart, byte-identical, while a remote view of the
same machine in the same window shows clearly different, live content. Only 2
displays exist (`screencapture -D3` errors "must be 1-2", confirmed via
`system_profiler`), so there's no hidden display explaining the gap.

This matches, almost verbatim, the warning already in this repo's own `KICKOFF.md`
and `CLAUDE.md`: ungranted Screen Recording permission causes `screencapture` to
return bad frames that look like a device problem but aren't ("Check this before
concluding anything"). That pre-flight check was not done before this session's
probe. **Fix: grant Screen Recording to whatever terminal hosts Claude Code, in
System Settings → Privacy & Security → Screen Recording, then restart the
terminal**, before trusting any local capture here.

## Interleave locus test — best available evidence, not a clean answer

With local capture unreliable, the only live-content evidence is the user's Screen
Sharing screenshot (twice-compressed: Screen Sharing's own video codec, then saved
as PNG). Analysis (crops and a scanline in `findings/2026-07-16-remote-view/`,
gitignored):

- The content is **one coherent portrait**, not a ~5-tile quilt grid.
- A clean flat-region scanline shows smooth gradient, no strong periodic
  banding/stripe signature at a regular pitch.
- Fine vertical fringing visible in flat regions (wall, forehead) is at least as
  well explained by ordinary video compression (chroma subsampling, block
  quantization) as by genuine subpixel interleave.

**Working read: leans toward "clean 2D image" (device-side), not confirmed.** See
`probe/DECISION.md` §3 for the full writeup. A real local capture after fixing
Screen Recording permission should settle this outright — either it shows the same
clean image (confirms device-side) or it reveals stripes/moiré invisible in the
compressed version (host-side).

## Session 2 (~13:02, same day) — permission grant didn't fix it; found the real cause

Owner granted Screen Recording in System Settings. Re-ran the full probe from this
Claude Code session anyway: `screen-2.png` is still a wallpaper-only placeholder
(no Napster content), byte-different from session 1's captures but the same kind of
non-answer.

**Root cause: this session runs over SSH**, confirmed by walking the process tree
(`sshd-session → zsh → claude → zsh`). Screen Recording's TCC grant attaches to a
windowed app (Terminal.app, iTerm2, ...); an SSH shell has no window-server identity
to attach to, so `screencapture` here can never see live content, regardless of what
gets granted in Settings — macOS just returns the desktop-picture placeholder
instead of erroring. Granting permission to *some* terminal app doesn't help unless
the capture is actually run from inside that app's own local session.

**Corrected path forward:** run `probe/run-probe.sh`'s framebuffer step from a
Terminal window opened locally at the mini's console (or a Screen-Sharing session
with control, not this remote session), with Screen Recording granted to that
specific app. This session can still do all the downstream analysis — it just
cannot be the one holding the camera.

Also from this run: EDID (`ioreg -lw0 -r -c IODisplayConnect` / `-c AppleCLCD2`,
the repo's own targeted query, not the earlier generic one) came back empty again —
looks structurally unavailable via `ioreg` here, not a wrong-query issue. Napster
app-bundle string recon indicated a conventional Metal/AVFoundation real-time
video pipeline, but **no strings naming quilt geometry, lenticular pitch, view
counts, or calibration constants**. Symbol names are not reproduced here — the
absence is the finding, and the extracted strings are third-party binary content
that this repository does not redistribute.

Full detail in `probe/DECISION.md` §8.
